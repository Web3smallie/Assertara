# Assertara Phase 3 — Provenance Signing and Attestation

Offline cryptographic authorship for Phase 2 provenance manifests. A
dedicated Assertara attestation key signs the exact manifest digest; judges
verify the signature against a root-signed key registry obtained
out-of-band.

## 1. What a signature proves (and does not prove)

A valid attestation proves: **the identified Assertara attestation key
signed this exact manifest digest** in the Assertara provenance context
(chain id 5042002, reserved for future Arc Testnet anchoring).

It does NOT prove:

- that a model provider actually executed any model (no provider receipts);
- that the investigation records are true (a compromised server plus an
  inattentive operator can still sign false-but-valid packages);
- that any payment succeeded (check the transaction hash on the explorer);
- that the mandate/policy decision was correct (it commits to the decision,
  it does not re-evaluate it).

## 2. Key roles — four-way separation (non-negotiable)

| Role | Purpose | Must never |
|---|---|---|
| User wallet keys | User's own funds | Be requested, collected, stored, imported, or accessed by Assertara — no exceptions |
| Transaction-signing key (`SIGNER_PRIVATE_KEY`) | Controlled execution | Sign attestations; be visible to the attestation subsystem |
| Attestation key (`ATTESTATION_SIGNING_KEY`) | Sign provenance manifests | Authorize, sign, or broadcast transactions |
| Registry root (`REGISTRY_ROOT_KEY`) | Sign registry updates | Double as a day-to-day attestation key; touch any server |

The attestation subsystem (`src/services/provenanceAttestation.js` plus
`src/attestation/*.js`) contains **no** transaction-signing, wallet, RPC,
broadcast, HTTP, SDK, or agent code. This is enforced by automated
negative tests (N1–N9 in `test/unit/provenanceAttestation.test.js`), not
by convention. There is no key-import path: keys enter only via
environment variables at ceremony time, or are freshly generated by
`keygen.js`.

## 3. Generating keys

Attestation day key and registry root key are generated the same way, on
the operator's controlled machine. Never on a server.

```sh
# Preferred: protected file export (refuses to overwrite; refuses paths
# inside the repository; never prints the key).
node src/attestation/keygen.js --out /secure/offline/att-day1.key --role attestation
node src/attestation/keygen.js --out /secure/offline/att-root.key --role root

# Explicit one-time stdout export ONLY (diagnostics stay on stderr).
node src/attestation/keygen.js --export --role attestation
```

- `--out` applies owner-only protection (POSIX `0600`, verified) or a
  Windows ACL lockdown (inheritance removed, current user only), then
  **proves** read/write still work before the key is written. If hardening
  is unavailable it warns loudly and uses directory-default permissions —
  ensure the directory is private. If the file would be unreadable back,
  nothing is written and the operator retries (no key is ever lost or
  half-written).
- With no export flag the tool refuses to run: a generated-but-unexported
  key would be lost.
- Back up the file offline immediately. Loss without backup is
  unrecoverable; there is no recovery path.
- Validate the printed address against the registered expected address
  before first use, and confirm it is not on the deny-list
  (`ATTESTATION_DENY_ADDRESSES`: signer, operator, deployment addresses).

## 4. Root trust bootstrap — two independent channels

The root public key cannot authenticate itself. Before any registry is
trusted, its fingerprint (`sha256(lowercase-address)`, printed by
`keygen.js` and `registry.js sign`) must be published through **two
genuinely independent channels**:

1. **Signed git tag + release artifact** in the official Assertara
   repository (e.g. tag `attestation-root-v1` carrying `SIGNED-ROOT.txt`
   with the fingerprint and the registry digest it anchors).
2. **DNS TXT record** at a designated name (e.g.
   `_assertara-attestation-root.<project-domain>`) administered under
   **separate credentials** from the repository (registrar access ≠ repo
   access). If DNS is unavailable, the second channel must be a
   publication under separate administrative control (a different
   person/org's repository or gist) — the criterion is that compromising
   the repository alone must not compromise the second channel.

Release notes and `docs/attestation.md` inside the same repository do
**not** count as two channels.

**Judge rule:** fetch the fingerprint from both channels independently and
require **byte-equality**. On mismatch — or if either channel is
unreachable — stop: do not trust the registry. Then verify the registry
signature against that root (`registry.js verify --trusted-root`), check
the version is the latest you expect (`--min-version`), and confirm
freshness (default: refuse registries older than 180 days unless you
explicitly accept staleness).

**Root compromise recovery:** there is no in-band root rotation. Generate
a fresh root, publish its fingerprint through both channels again, sign a
new registry whose `supersedes` field names the old root and version, and
treat all attestations under the compromised root as untrusted
(re-attestation required). Old registry history is preserved for audit,
never rewritten.

## 5. Registry lifecycle

```sh
node src/attestation/registry.js init --out reg-v0.json --key 0xDAY1 --reason "genesis day key"

# Load the root key WITHOUT placing it in shell history or the process
# table prefix: interactive invisible entry (nothing echoed), use, unset.
read -s REGISTRY_ROOT_KEY -p "registry root key: "; echo
export REGISTRY_ROOT_KEY
node src/attestation/registry.js sign --registry reg-v0.json --out reg-v0.signed.json
unset REGISTRY_ROOT_KEY
# (PowerShell equivalent: $ss = Read-Host "registry root key" -AsSecureString;
#  $env:REGISTRY_ROOT_KEY = [Runtime.InteropServices.Marshal]::PtrToStringAuto(
#    [Runtime.InteropServices.Marshal]::SecureStringToBSTR($ss));
#  ... run sign ...; Remove-Item Env:\REGISTRY_ROOT_KEY)

node src/attestation/registry.js verify --registry reg-v0.signed.json --trusted-root 0xROOT
node src/attestation/registry.js add --registry reg-v0.signed.json --trusted-root 0xROOT --out reg-v1.json --key 0xDAY2 --reason "rotation"
# ... sign v1, then:
node src/attestation/registry.js retire --registry reg-v1.signed.json --trusted-root 0xROOT --out reg-v2.json --key 0xDAY1 --reason "routine rotation" --superseded-by 0xDAY2
node src/attestation/registry.js revoke --registry reg-v2.signed.json --trusted-root 0xROOT --out reg-v3.json --key 0xDAY9 --reason "suspected exposure" --status COMPROMISED
```

Rules:

- Every mutation is built from a **signature-verified** predecessor:
  version must increment by exactly one, key states move monotonically
  (`ACTIVE → RETIRED → REVOKED/COMPROMISED`; terminal states never leave;
  `COMPROMISED` can never be rehabilitated).
- Mutations write **unsigned** successors (`--out` must not exist);
  nothing is trusted until `sign` with the offline root key.
- `sign` refuses if the root key appears as a day-to-day attestation key.
- Key states and judge-facing meaning:
  - `ACTIVE` — verifies normally.
  - `RETIRED` (planned rotation, no compromise suspected) — historical
    trust requires **independent corroboration** (release artifact,
    published digest, future on-chain anchor) that the attestation
    existed before retirement. The signed `issuedAt` is self-asserted
    and never counts as trusted time.
  - `REVOKED` — untrusted unless the caller explicitly overrides (and
    the override is labeled as such, still `ok:false`).
  - `COMPROMISED` — untrusted, no override; re-attestation required.

## 6. The attestation ceremony

```sh
# Public addresses are safe inline; the PRIVATE ceremony key must NEVER
# appear in a command line, export statement, or shell history.
export TRUSTED_ATTESTATION_AUTHORITIES=0xDAY1
export TRUSTED_REGISTRY_ROOT=0xROOT
export ATTESTATION_DENY_ADDRESSES=0xSIGNER,0xOPERATOR

# Private key: interactive invisible entry (ceremony time only), use, unset.
read -s ATTESTATION_SIGNING_KEY -p "attestation key: "; echo
export ATTESTATION_SIGNING_KEY

# 1. Preview (always first; without --acknowledge it writes nothing,
#    attested:false).
node src/attestation/attest.js --package pkg.json --expect-digest <64-hex> \
  --registry reg-v1.signed.json --min-registry-version 1

# 2. Confirm (only after reading the preview).
node src/attestation/attest.js --package pkg.json --expect-digest <64-hex> \
  --registry reg-v1.signed.json --min-registry-version 1 --confirm

unset ATTESTATION_SIGNING_KEY
```

Key-hygiene rules (all Phase 3 private keys):

- Never type a private key into a command (`KEY=0x... cmd`), an `export
  KEY=0x...` line, a script, or any file under the repository — all of
  these persist the secret (history, disk, process table).
- Never place Phase 3 variables in the repository `.env`: `src/config/env.js`
  loads `.env` into every server/agent process, which would expose the
  ceremony key outside the offline ceremony.
- Prefer `read -s` (above). The alternative is a restricted env file
  (`umask 077`, owner-only, outside the repo): `set -a; source
  /secure/offline/att.env; set +a`, run the ceremony, `unset` the key,
  then delete the file. Never `echo` the key into the file — write it
  with an editor and verify permissions before use.
- Environment variables are still visible to privileged processes on the
  machine while set — that is why keys are loaded at ceremony time and
  unset immediately after, on the controlled operator machine only.

Ceremony rules:

- `--expect-digest` (full 64 hex) binds your intent to the exact manifest;
  the digest is recomputed and must match. Bare-digest signing is
  refused: the manifest must exist in the persistent manifest store.
- Production ceremonies must pass `--min-registry-version` with the
  latest registry version you expect: without it a rolled-back registry
  is not refused automatically (the version is shown in the preview, but
  only the flag enforces it). `--max-registry-age-days` likewise bounds
  staleness; both reject malformed numerics instead of disabling the
  check.
- A package combining a `BLOCK`/`UNCERTAIN` agent decision with an
  executed transaction hash is refused as contradictory
  (`ATTEST_DECISION_INCONSISTENT`): BLOCK/UNCERTAIN never receive
  execution approvals, so the package or its source records are corrupt.
- The manifest store is rechecked at four checkpoints (before preview,
  before signing, before each append): if the reviewed manifest
  vanishes, its investigation becomes unlistable, or a newer manifest
  appears, the ceremony aborts unconditionally — overrides never apply
  past the preview. Residual risk: no shared manifest-store lock
  exists, so a manifest landing between the last recheck and the append
  is theoretically possible; it cannot cause a false attestation (the
  signature stays digest-bound to the reviewed manifest).
- The preview shows investigation id, full digest, model provenance,
  decision, evidence digests, transaction + receipt info, key identity,
  registry version, case letter, and warnings. Cases:
  - **A** valid complete (default) · **C** pre-execution (re-attest after
    execution) · **D** post-execution receipt-backed · **E** BLOCK /
    unreleased REVIEW (signs; no transaction expected) — sign normally.
  - **F** execution claimed without receipt evidence — refused unless
    `--allow-unverified-execution` is also given; verify the hash on the
    explorer yourself first.
  - **G** superseded manifest — refused unless `--allow-superseded` is
    given; prefer attesting the latest manifest instead.
  - **B-condition** (incomplete model evidence) rides along as an explicit
    flag + warning on any letter.
- `attested:true` is reported only after the attestation **and** its audit
  event are both verified as persisted. Signing, attestation persistence,
  audit persistence, and completion are distinct lifecycle events; a retry
  after a crash adopts existing valid records instead of duplicating them
  (same `(manifestDigest, keyId)` identity, signature verified, never
  blindly re-signed).
- If any store holds malformed, blank, or shape-invalid records (valid
  JSON with the wrong shape counts), or an ambiguous torn tail, the
  ceremony fails closed. Inspect with `--reconcile`, acknowledge
  specific bytes with `--acknowledge` (offset/length/sha pinned,
  rationale required), and re-run. Original bytes are never rewritten.
  Note: a preview run WITH `--acknowledge` DOES append the journal ack
  records (under the lock, before confirmation) — preview first without
  it, then re-run adding acks.
- The reconciliation journal itself is gated the same way: complete
  journal corruption blocks new ceremonies and journal mutations
  (`--amend`/`--note`) until every debris item has usable acknowledgment
  coverage (see §8). A journal **chain break** blocks permanently for
  that store: preserve it for forensics and continue in a fresh store
  directory if needed — never delete or overwrite the old store.
- Only one ceremony may run at a time (exclusive lock, fail-fast). If a
  previous run died holding the lock, `--break-lock` quarantines it only
  when demonstrably stale (old **and** owner dead); pass the quarantined
  path via `--lock-broken` so the break lands in the audit event. A
  **zero-byte lock file** (crash between lock creation and content
  write) is unparseable: the ceremony reports the lock held and
  `--break-lock` refuses it — confirm no ceremony is running (process
  list + lock-file timestamp), delete the empty file manually, and
  re-run. There is no automated path, by design.
- `--status` is observational only (never `attested:true`). `attest.js
  --verify --digest` re-checks completion under the lock and is
  authoritative. Do not confuse it with `registry.js verify`, which
  checks the registry root signature and freshness — different tool,
  different trust question.

## 7. Judge-side verification (offline, no trust in Assertara's servers)

Given a v2 verification package (`packageVersion:
assertara-verify-2`), the signed registry, and the root fingerprint from
**both** publication channels:

1. Confirm the two fingerprints are byte-equal; abort otherwise.
2. `registry.js verify --registry reg.json --trusted-root 0xROOT
   --min-version <latest-you-expect>` — must print VALID.
3. Recompute digests from the disclosed package (Phase 2
   `verifyPackage`: public projection, request projection, manifest).
4. Verify the attestation signature + key state (`verifyAttestation` with
   your trusted authorities list): `valid`, or `trusted-historical` with
   corroboration you checked yourself for retired keys.
5. If a transaction hash is present, inspect it on the Arc Testnet
   explorer yourself (receipt status, block). An attestation never turns a
   hash into proof of payment.

## 8. Reconciliation journal

`data/attestation-reconciliation.jsonl` records operator acknowledgments
of store corruption, linked by a cumulative hash chain (every byte of
every line contributes). `--reconcile` shows debris; `--amend` appends a
linked rationale amendment (originals immutable); `--note` appends
context. The chain gives **internal tamper evidence**, not independent
authenticity: the controlled operator machine remains the trust root for
acknowledgments, and a full journal rewrite from genesis is undetectable
without an externally published tip (future hardening, not Phase 3).

Fail-closed journal rules (what `--reconcile` shows is what gates):

- Every complete journal line is valid, blank, malformed, or
  shape-invalid — nothing is silently skipped. Any corruption blocks new
  ceremonies and journal mutations until acknowledged.
- Acknowledge journal debris exactly like other stores: `--reconcile`
  reports the byte offset, length, SHA-256, acknowledgment id, and
  suggested classification (`foreign-debris` for malformed/shape-invalid,
  `blank-line` for blanks); pass entries with `store: "journal"` via
  `--acknowledge` with your rationale. Bytes are re-read and re-verified
  under the lock — any change invalidates the acknowledgment, which
  records disposition only and never promotes debris into a trusted
  record. Pre-existing valid acknowledgments keep working.
- A chain break (`chainPrev` mismatch) is unrecoverable: no override,
  no resumption marker. Read-only inspection (`--status`, `--reconcile`,
  `--verify`) keeps working for forensics, but the store takes no new
  writes. Preserve it and continue in a fresh store directory.
- `--amend`/`--note` refuse while corruption is present, with one
  exception: an amendment targeting an already-contested acknowledgment
  is itself recovery, so it is permitted on an unbroken chain.

## 9. Stores and files

- `config/attestation-keys.json` — registry location (placeholder until
  the operator initializes it via `registry.js init` + root signing).
- `data/manifests.jsonl` — Phase 2 manifests (read by the ceremony for
  continuity; never written by it).
- `data/attestations.jsonl` / `data/attestation-audit.jsonl` — append-only
  attestation + audit stores (exclusive lock, fsync + re-read verify).
- `data/attestation-reconciliation.jsonl` — append-only acknowledgments.
- `.attestation-ceremony.lock` + `.attestation-lock-quarantine/` — live
  lock and quarantined stale locks (quarantine preserves bytes).

## 10. Limitations and residual risks

- The ceremony cannot prove the source records are true — only that the
  operator saw and signed this exact package. Review previews skeptically.
- The registry root is the ultimate trust anchor until Phase 4 on-chain
  anchoring; its two-channel publication is load-bearing.
- Revocation propagates only via fresh registries; always check version
  and freshness.
- Durability covers process/OS crashes (fsync + re-read), not storage
  devices that lie about flushes, or network filesystems (local disk
  required). Windows cannot fsync directories (NTFS journaling covers the
  common case).
- Key loss without backup is unrecoverable by design.

## 11. Step 6 — On-chain publication and judge verification

Step 6 connects the Phase 1–3 provenance chain to the Step 4
`ProvenanceAttestation` contract: manifest → Phase 3 ceremony signature →
publisher submission → off-chain export → judge verification. No Step 6
component mints attestation signatures; all trust still roots in the
Phase 3 ceremony and registry (§4–§6).

### 11.1 Key roles — publisher separation (non-negotiable)

Step 6 adds exactly one key role:

- `PUBLISHER_TX_KEY` — pays gas and sends `attest(...)` transactions
  only. It holds no provenance authority and can never create an
  attestation signature.

The publisher mechanically refuses to submit when the publisher
address equals the recovered attester, the registry root, or any
deny-listed address (`PUBLISH_KEY_CONFLICT`). It must also differ
from the controlled transaction signer, operator, deployment, and
wallet keys. The attestation key signs provenance; the publisher key
submits it; the controlled signer moves value. No key may serve two
roles. No KMS/HSM in this milestone: custody is file/env-based (see
§3 rules — never in shell history, never in the repository `.env`).

### 11.2 Publisher runbook

`src/services/attestationPublisher.js` accepts an already-signed v2
package and the signed registry. It verifies everything before
submitting, and verifies everything again after:

1. `verifyPackage` + digest recomputation (no trust in envelopes).
2. `verifyAttestation` (signature, registry root, freshness, ACTIVE
   key) and signer recovery — the recovered address becomes the
   on-chain `attester` (never `msg.sender`).
3. Decision/bitmap/txHash derivation from the verified manifest
   (§11.4). BLOCK/REVIEW with a transaction hash refuse;
   UNCERTAIN is unrepresentable and refuses.
4. Key-separation checks (§11.1).
5. Duplicate pre-check against `getAttestation`: an identical
   on-chain record skips submission; any differing field refuses
   with `PUBLISH_CONFLICT` (mirrors the contract).
6. Submission, receipt wait (configurable `--confirmations`
   equivalent `confirmations`), then independent verification:
   receipt status, contract read-back, and decoded `Attested`
   event contents must all match, or publication fails.

Programmatic use (operator machine; key via env, never argv):

```js
const { publishAttestation } = require('./src/services/attestationPublisher');
const result = await publishAttestation({
  signedPackage: v2,            // ceremony output (manifest + attestation)
  registry,                     // signed registry object
  trustedRoot: '0xROOT',
  trustedAuthorities: ['0xATTESTER'],
  denyList: ['0xSIGNER', '0xDEPLOY'],
  rpcUrl: 'https://rpc.testnet.arc.io',
  chainId: 5042002,
  contractAddress: '0xCONTRACT',
  publisherKey: process.env.PUBLISHER_TX_KEY,
  confirmations: 2
});
```

The result's `checks[]` array records every verification step;
`duplicate: true` means the identical record already existed and
nothing was submitted. RPC trust note: receipt + read-back + event
cross-checks mitigate a lying endpoint, but reorg windows remain —
raise `confirmations` for finality-sensitive publications.

### 11.3 Off-chain manifest publication

`src/attestation/exportPackage.js` builds the portable, digest-bound
export file (content-addressed, static-hostable):

```sh
node src/attestation/exportPackage.js --package v1.json \
  --attestation attestation.json --expect-digest <64hex> \
  --out <manifestDigest>.export.json
```

- `--expect-digest` binds operator intent; the digest is recomputed
  from the manifest bytes before export and must match.
- `--out` uses exclusive creation: an existing file refuses, never
  silently overwrites.
- The export contains only the manifest, the public projections
  already in the v1 package, and the attestation object. No private
  keys, audit records, operator secrets, or evidence bytes beyond
  the v1 disclosure boundary.
- Publish the file anywhere content-addressed (release artifact,
  static hosting, direct handoff); the manifest digest is its
  identifier and its integrity check.

### 11.4 Model bitmap semantics

The on-chain bitmap derives from verified manifest contribution
levels only — never from configured stages or pipeline labels:

- Bit 0 (Muse Spark): `SUCCEEDED`, `OUTPUT_INCLUDED`,
  `VERDICT_ACCEPTED`.
- Bit 1 (SAM 3.1): `SUCCEEDED`, `OUTPUT_INCLUDED`,
  `PROMPT_INCLUDED`, `VALIDATED_AGAINST`.
- Every other level (`PARTIAL`, `MOCK`, `INVOKED`, `FAILED`,
  `TIMEOUT`, `NOT_INVOKED`, …) clears its bit.

Current transaction-agent investigations honestly report SAM
`NOT_INVOKED` (Step 5), so bit 1 is legitimately 0 there.

### 11.5 Judge verification (no private keys)

`src/attestation/judge.js` is read-only and accepts no private keys:

```sh
node src/attestation/judge.js --rpc <url> --contract 0xCONTRACT \
  --investigation <evalId> --attester 0xATTESTER \
  --manifest-file <digest>.export.json \
  --registry registry.json --trusted-root 0xROOT \
  --min-version <N> --max-age-days 30
```

It prints per-step PASS/FAIL and exits non-zero unless every
required check passes: chain record → export fetch → digest
recompute → digest-vs-chain → package integrity → signature →
signer-vs-attester → registry trust + ACTIVE key → decision /
bitmap / txHash agreement → receipt + event match → BLOCK/REVIEW
no-payment statement. `--manifest-url` may replace `--manifest-file`
for remote exports; `--submit-tx` pins the submission receipt,
otherwise the judge locates the `Attested` log itself.

Independence statement: the judge reuses Assertara's own
verification code, so running it trusts the codebase to check
itself. Genuine independence comes from the evidence being
re-checkable without it: canonical JSON + SHA-256 are documented,
the EIP-191 signature verifies with any secp256k1 library, and the
on-chain record is world-readable. "Independent verification" here
means no access to Assertara's private keys, servers, or internal
stores is required.
